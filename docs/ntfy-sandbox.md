# One-module ntfy sandbox evidence (not stack acceptance)

## Scope and immutable selection

The only executable service module in this slice is the **single** named `ntfy` catalog module. The code hardcodes Docker Hub's official upstream repository `docker.io/binwiederhier/ntfy` and its linux/amd64 v2.35.0 **manifest digest**:

`docker.io/binwiederhier/ntfy@sha256:8a3e2036faf218acefd3c25b16659e846df39814d2e3caae1a1ac4e737ee4f2d`

The Docker registry's TLS API returned tag `v2.35.0` as multiarch index `sha256:6f0c9abab7b99a978d816611cc90dabb4849b81f60c53114e91cd07931085dc0` with linux/amd64 manifest `sha256:8a3e2036faf218acefd3c25b16659e846df39814d2e3caae1a1ac4e737ee4f2d`. Fetching that manifest by digest produced the **same** `Docker-Content-Digest` header and SHA-256 of its 950-byte response. Rootless Podman pulled **only that digest** into `/mnt/media/p0-v3/platform-lifecycle-sandbox/ntfy-fixture/podman-root`; `image inspect` showed repo digest equal to the selected digest and local config ID `a080fe345c08dd54faeb5a8121c035e74a823f111cf9209bd228b886474e15b7`. Upstream's [install guide](https://docs.ntfy.sh/install/#docker) identifies this repository and persistent cache directory; its [config guide](https://docs.ntfy.sh/config/#message-cache) describes the on-disk SQLite cache. This is transport/digest verification, **not** a signature, SBOM, reproducible-build or supply-chain audit.

No tag is passed to the executor. `module ntfy prepare|install|stop|remove|snapshot|restore|restore-remove` has **no arbitrary image, port, volume, module or host path parameter**; only snapshot/restore/remove-restore take a bounded ID. `prepare` requires existing, owner-only `0700` roots `/mnt/media/p0-v3/platform-lifecycle-sandbox` and `/mnt/media/p0-v3/backup` and creates guarded `ntfy-fixture` children with binding marker. Podman is forced local, rootless, site-private `vfs` root/runroot, `--pull=never`, read-only rootfs and limited capabilities/resources. Container port 8080 is published **only** at `127.0.0.1:18486` (isolated restored target at `127.0.0.1:18487`). No public route, 443, Cloudflare, systemd, useradd, software_lab mount, auth or agent capability changes. The first disposable attempt tried port 80 with dropped capabilities; ntfy exited with `bind: permission denied`. This was corrected to unprivileged container port 8080 before successful testing. An `install` command only checks start and running status; functional health is separately tested.

## Actual result, 2026-10-30 UTC

1. In the guarded `ntfy-fixture` store, `module ntfy install` started ntfy 2.35.0. `ss` showed **only** `127.0.0.1:18486` listening. `GET /v1/health` returned `{"healthy":true,"role":"active"}`. A loopback `POST /p0v3-fixture-topic` with `ntfy-sandbox-first-publish` returned a ntfy message; `GET /p0v3-fixture-topic/json?poll=1` returned the same message.
2. `module ntfy stop` completed before `module ntfy snapshot first`. This copied the stopped SQLite `cache.db` (65,536 bytes) to `/mnt/media/p0-v3/backup/ntfy-fixture/first` with a SHA-256 manifest. `cache.db` SHA-256: `39fcde70caffe1b48d1a8eb3e08dbe1f0d8566d7101360a3151cdfc5d375e908`.
3. `module ntfy restore first` verified backup bytes, created a **different** sandbox data target under `restores/first` and started a **different** container bound only to `127.0.0.1:18487`. The cached original message was returned by `GET .../json?poll=1` from the restored server. The original `data/` was not overwritten. `restore-remove first` removed the isolated restore container; `remove` removed the original container while retaining data, image and backup.
4. Two further sandbox `install`/publish/read/`stop`/`remove` cycles succeeded. Each saw the original persisted message and published a distinct `ntfy-sandbox-second` or `ntfy-sandbox-third` message. The private `podman ps -a` was empty after teardown and neither sandbox port was listening.
5. The **opt-in real integration test** `NtfyRealIntegrationTest` was run successfully twice against the same guarded roots with new snapshot IDs. It published/read a unique message, stopped and backed up SQLite, restored into a separate container, read the old message and published/read a new one there, then ran two reinstall/publish/read/teardown cycles. Example retained snapshot SHA-256: `381cb3f1f521a0781a8c7ffd39e654668771b20b78e924aac9946c5fbd9efa26` at `backup/ntfy-fixture/it840vh0kb3f/cache.db`, and `44983a4cef9c8148472deecd0bcc2b2e3c56cb9cdc48bd0998eb401806a3344f` at `it841rpdv7qz/cache.db`. The backup manifests remain available under the guarded backup directory. No container or port remained active afterward.

Run the opt-in test only when the pinned digest is already preloaded into that isolated Podman store, both sandbox and backup roots are reviewed and owner-only, and the loopback ports are free:

```sh
P0V3_NTFY_SANDBOX_INTEGRATION=1 JAVA_HOME=/usr/lib/jvm/java-21-openjdk-amd64 GRADLE_USER_HOME=/mnt/media/p0-v3/cache/gradle-user ./gradlew test --tests 'net.datamancy.platform.NtfyRealIntegrationTest' --offline --rerun-tasks
```

Ordinary `clean check` does **not** touch real Podman: it runs fake-backend tests and skips this one opt-in test. It does enforce the JaCoCo production LINE gate. The real test is bounded to one public-write localhost instance with a single SQLite cache, one snapshot at a time, at most three flat cache files of up to 64 MiB each. No auth, SSO, HTTPS, multi-service dependencies, actual site route, durable scheduled backup, external clients, or other inventory module has been accepted. This does **not** count toward two back-to-back *full-stack* installs/restores: **0/2**.
