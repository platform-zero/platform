# Disposable Keycloak + PostgreSQL identity sandbox (NOT production SSO)

Scope: **only** a synthetic `p0v3-sandbox` realm, two fake subjects (`sandbox-human` and `sandbox-agent`), a test-only public client, an optional database-only marker user, and a disposable PostgreSQL backend. This does **not** deploy the inventory `keycloak` module (which also lists `keycloak-bootstrap`), an authorization gateway, real browser login, host lane accounts, equal application policy, routes, or any other inventory service. Full-stack acceptance: **0/2**.

## Contract and isolation

- Keycloak: official `quay.io/keycloak/keycloak@sha256:3e1ac632e743660017b1e6bb4c3ffc800fd02c82cdd0db858cd03456a98a8dfc` (linux/amd64 OCI manifest for 26.8.1; fetched from Quay's manifest endpoint, matching `Docker-Content-Digest`). PostgreSQL: official `docker.io/library/postgres@sha256:2c42c21a8909d1b656ac93348db2862b6bad38091a9b0d3d1485479465802013`. Both were pulled by digest **only** into the new `identity-fixture` private rootless `vfs` store. No other sandbox's PostgreSQL store or live service is used.
- The guarded `0700` sandbox is `/mnt/media/p0-v3/platform-lifecycle-sandbox/identity-fixture`. Its owner/image marker, fake credentials, realm file, data, restored data, Podman `--root`/`--runroot`, and owner-guarded `0700 network-config/` are separate from the ntfy and PostgreSQL fixtures. **Every identity Podman command**, including network create/list/remove and container operations, supplies `--network-config-dir=<identity-fixture>/network-config`. A site-local `0600 containers.conf`, supplied through this process's `CONTAINERS_CONF`, selects `slirp4netns` for the private network namespace. The initial default `pasta` helper could not open its PID file in the private runroot; no host permission or shared-home workaround was applied. `netavark.lock` is allowed only inside the guarded directory. Unexpected definitions, symlinks, broad directory permissions, or a changed local helper config block operations.
- Primary private network: `p0v3-identity-net`; each restore uses a separate network and data directory, e.g. `p0v3-identity-net-oidc-mvvgt7mk`. Database port **is not published**. Only `127.0.0.1:18580` (primary) and `127.0.0.1:18581` (restore) publish HTTP for these opt-in tests. No public ingress, DNS, TLS, host port 443, host accounts, operator secrets, or `software_lab` changes. Keycloak's container UID 0 remains inside **rootless** Podman; it is not host root.
- The realm fixture is imported through Keycloak's documented `/opt/keycloak/data/import` and `start-dev --import-realm`; existing realms are skipped on startup. It has explicit synthetic names, IDs, profile fields and generated **fake** passwords. The client sets `directAccessGrantsEnabled=true`, `standardFlowEnabled=false`, and `fullScopeAllowed=false`. The direct **password grant is test-only**, deliberately avoids real browser SSO, and must never be promoted as a production authentication policy. Fake credentials are created under owner-only storage and never passed in command arguments or printed in tests. No production client, issuer, redirect, consent, roles, user provisioning, or authorization contract is inferred.
- Keycloak is stopped for the PostgreSQL `pg_dump -Fc`, so the database is quiescent; the backup also contains the exact fake import file, Keycloak env/config and PostgreSQL fake password. The dedicated `0700` `/mnt/media/p0-v3/backup/identity-fixture/<id>` contains owner-only `0600` artifacts and a SHA-256 manifest. An incomplete `.pending-*` is **retained**, never treated as success or silently deleted. An isolated new PostgreSQL container restores that dump before its separate Keycloak starts. `remove`/`restore-remove` stop and delete only the explicitly named containers and private network definitions; persisted data and backup evidence remain. **No timer or retention policy** is installed.

Keycloak references: [official container](https://www.keycloak.org/server/containers), [startup import and existing-realm skip](https://www.keycloak.org/server/importExport), [OIDC discovery/token endpoints](https://www.keycloak.org/securing-apps/oidc-layers). These upstream interfaces support a **synthetic test fixture**, not an approved site identity contract.

## Commands and actual tests

Use Java 21, `GRADLE_USER_HOME=/mnt/media/p0-v3/cache/gradle-user`, `--offline`. Explicit CLI: `./gradlew run --args='module identity prepare'`, then pull both pinned images into the private store with **all** of `--root`, `--runroot`, `--storage-driver=vfs`, and `--network-config-dir=<identity-fixture>/network-config` plus `CONTAINERS_CONF=<identity-fixture>/containers.conf` (not the normal Podman store). The fixed `module identity install|stop|remove` and `module identity backup|restore|restore-remove <id>` require the owner guard. Do not start against occupied ports or without approved v3-only paths. The real test requires an explicit opt-in:

```sh
P0V3_IDENTITY_INTEGRATION=1 JAVA_HOME=/usr/lib/jvm/java-21-openjdk-amd64 GRADLE_USER_HOME=/mnt/media/p0-v3/cache/gradle-user ./gradlew test --tests 'net.datamancy.platform.IdentityRealIntegrationTest' --offline --rerun-tasks
```

**Actual outcomes (2026-10-30 UTC):** The first rootless private-network start failed with `pasta` PID-file permission denied; after selecting site-local `slirp4netns`, private network create/start/remove succeeded. The initial two fake users were rejected as `Account is not fully set up`; adding explicit fake profile fields resolved login. The first opt-in test failed because Keycloak's Admin API chose its own database-marker subject ID instead of the requested ID; the test was corrected to read back the assigned ID. No failed run counted as acceptance. The corrected opt-in integration test passed **twice**: real discovery, password-grant access and ID tokens for both subjects, cryptographic RS256 verification against Keycloak JWKS and issuer/subject/expiry checks, an Admin-API-created **database-only** marker user absent from the import file, consistent backup, isolated restored PostgreSQL and Keycloak, and renewed verified tokens for all three users on the restored issuer while primary remained functional. A final rerun after mode/guard hardening also passed; the test's network lifecycle assertions observed only the expected private network definitions during primary/restore and none after teardown. The ordinary clean offline check passed with **1069/1167 = 91.60% production LINE coverage** (48 discovered, 44 executed, 4 real integrations skipped, 0 failures); the real test is skipped by default. The fresh target was initialized separately, but the **source fixture data was reused across reruns**, so these were not clean full-stack installs.

Retained successful backups: `oidc-mvvgpnre` and `oidc-mvvgt7mk`; earlier `oidc-mvvgms9g` was also a successful restore after the test-ID fix, while the first failing test occurred before its backup.
