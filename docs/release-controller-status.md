`release validate <lock.json> <sha256-file> <signature-base64-file> <trusted-ed25519-public-key-base64-file> <approved-hosts.json>` and `release plan ...` accept five owner-only regular nonsymlink inputs. The trusted Ed25519 public key must be provisioned and pinned independently of the release author; passing an attacker-chosen key defeats authenticity. The lock is strict JSON (`schemaVersion:1`, `products:[{id,upstreamVersion,processes:[{id,role,image,dependencies,readiness,secretKeys,userId,networks,stateIds,schedule?}],state:[{id,owner,containerPath,backupHook,restoreHook}],routes:[{host,processId,port}],journeys:[{id,outcome}]}]`). Roles are `DAEMON`, `ONE_SHOT`, `TIMER`; network roles are `APP`, `DATA`, `INGRESS` (ingress is restricted to the Caddy process). A timer requires an explicit bounded schedule, and every named state set needs a mount and an owning process. Every family must be present exactly once. Processes need digest syntax and named readiness, dependencies must exist and be acyclic, state must name its owner and hooks, journeys cannot be empty, public hosts need an independently supplied exact approval list. The checksum file contains the lowercase SHA-256 of the **exact lock bytes**. The detached Ed25519 signature authenticates these same bytes against the independently supplied trust key. Neither checksum nor signature verifies image registry provenance, approves upstream compatibility, proves a readiness check works or proves DNS reachability. `release plan` emits sorted dependency order, approved hostnames and state owners, with `executable:false`. `release status <private-journal-file>` checks an existing private hash-chained journal and returns its last record; it does **not** inventory live resources or attest that a recorded step occurred. These outputs are offline diagnostics, **not** a deployable plan.
