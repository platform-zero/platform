# Logical-service wiring research (30 October 2026)

**Research, not a deployment or approval.** The owner's original 89 container/job/helper IDs are evidence of capabilities required to deliver the selected services, not a v3 unit topology or a release gate. A provisional reduction is **40 logical service families**; the grouping is not a claim that only 40 processes will run. The v3 additions Keykeeper, OpenBao and Worklane/TUIOS are outside that historical list. No v3 integrated stack was started during this research; release remains **0/2**.

## Recommended graph

```text
approved external ingress (DNS, TLS, non-HTTP ports separately)
    -> Caddy / approved origin proxy -> private application frontends
    -> identity: Keycloak -> native app OIDC clients; Keycloak -> MAS -> Synapse -> Element
    -> app-specific API/WebSocket routes: Matrix, Huly, ERPNext, Mastodon, Seafile/ONLYOFFICE
private state networks:
    -> PostgreSQL and MariaDB: separate database/user per app
    -> Valkey and Memcached: separate keyspaces/instances where retention differs
    -> Huly: CockroachDB + Elasticsearch-compatible index + object store + Redpanda
private operations:
    -> metrics: node/app exporters -> Prometheus -> Alertmanager; Grafana reads metrics
    -> logs: Alloy -> Loki -> Grafana; notifications: ntfy, mail as appropriate
    -> consistent per-product dumps/snapshots -> encrypted Kopia repository -> isolated restore
```

**Connectivity, not a shared superuser:** one database server can host several independent application databases; give each app its own database/credentials and backup contract. Never blindly share a cache or search index across apps with different lifecycles. Publish only intended frontends; database, management, search, metrics and object-store ports stay private. Caddy supports HTTP/WebSocket proxying and health checks, but live origin 443 still requires an approved host ingress arrangement; a rootless process cannot bind it on this host as currently configured. Caddy reference: https://caddyserver.com/docs/caddyfile/directives/reverse_proxy . Keycloak explicitly says not to proxy its management port 9000 and to restrict trusted proxy headers: https://www.keycloak.org/server/reverseproxy .

MAS supports upstream OIDC and documents Keycloak specifically: https://element-hq.github.io/matrix-authentication-service/setup/sso.html . - **Files + office:** Seafile's integration instructions cover a separate ONLYOFFICE server and configuration/callbacks: https://manual.seafile.com/latest/extension/only_office/ . - **ERPNext and Firefly:** Frappe's production compose defines backend/frontend/websocket/queue/scheduler/configurator roles: https://raw.githubusercontent.com/frappe/frappe_docker/main/compose.yaml . - **Huly:** Official selfhost README warns its bundled CockroachDB and Redpanda settings might not be production-ready and directs version migration review: https://raw.githubusercontent.com/hcengineering/huly-selfhost/main/README.md . - **Identity:** BookStack OIDC uses the external `sub` subject and a specific `/oidc/callback`: https://www.bookstackapp.com/docs/admin/oidc-auth/ . Grafana documents Keycloak OAuth and roles: https://grafana.com/docs/grafana/latest/setup-grafana/configure-access/configure-authentication/keycloak/ . JupyterHub's OIDC authenticator uses discovery and recommends a verified unique username claim: https://oauthenticator.readthedocs.io/en/latest/tutorials/provider-specific-setup/providers/oidc.html .
- **Other joints:** SOGo uses IMAP/SMTP/database: https://www.sogo.nu/files/docs/SOGoInstallationGuide.html . Home Assistant's ntfy integration supports self-hosted URL and protected topics: https://www.home-assistant.io/integrations/ntfy/ . ## Quadlet implementation pattern for this host

On this host `podman --version` returned **5.4.2**. The version-matched Quadlet reference lists `.container`, `.network`, `.volume`, `.image`, `.build`, `.pod`, and `QUADLET_UNIT_DIRS=... podman-system-generator --user --dryrun` for isolated syntax verification: https://docs.podman.io/en/v5.4.2/markdown/podman-systemd.unit.5.html . The `.container` options in that reference include `Network=`, `Volume=`, `Secret=`, `EnvironmentFile=`, `HealthCmd=`, `PublishPort=` and security controls. Use generated `.service` names for `After=`/`Requires=`; `After=` only orders starts and does **not** prove SQL, an OAuth issuer or a browser journey is ready.

1. Represent each logical product as a **release contract** (version/digest, actual internal processes, dependencies, secrets, state, health and meaningful user action). Choose multiple Quadlets only when required by its documented version. No unit is generated merely because an old ID existed.
2. Render immutable digest-pinned Quadlets and owner-private config/secrets into a v3-only staging directory. Check generator dry-run and generated dependency graph **before** installation. Stage images, data mounts, private network(s), DBs/cache, then identity, applications, cross-product integrations, finally ingress and functional checks. Use narrowly scoped systemd timers for actual periodic jobs, oneshots for migrations/bootstraps; never treat a successful process start as proof of app readiness.
3. The stack controller is a versioned release/health gate, not `systemctl start everything` and not a true atomic transaction over databases. During development all ingress is loopback/private and does not change production DNS or existing routes. For a real cutover, verify endpoints/SSO/data/cross-app journeys before switching approved ingress; snapshot/restore and rollback data where a migration is non-reversible. Route changes and external mail/federation actions need separate approval.
4. Acceptance is **logical-service journeys**, plus meaningful helper outcomes where required by the chosen product architecture, backed by a complete clean install and an isolated functional restore twice. The current 89-ID acceptance gate is obsolete as a product gate and must be replaced rather than reported as 96 outstanding product checks. Unit coverage >=90% remains a separate constraint. Off-host backup durability remains deferred and its risk must be stated.

**Open release-specific verification, not evidence that the chosen set is incompatible:** selected image digests/versions, exact app OIDC behavior, Huly search backend (do not conflate OpenSearch and Elasticsearch), Redis-client semantics on Valkey, RTC UDP/TURN reachability, mail identity/deliverability, installer side effects and real-host ingress. These should be resolved in an actual v3-only integration loop, not by reinstating the old container-count gate.
