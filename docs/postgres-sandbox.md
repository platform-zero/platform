# One-module PostgreSQL sandbox evidence (not stack acceptance)

## Selection and boundaries

The only new executor here is the explicitly selected **`postgres`** inventory ID. It uses the Docker Official Image `docker.io/library/postgres` version `17.11-alpine3.23`, linux/amd64 manifest:

`docker.io/library/postgres@sha256:2c42c21a8909d1b656ac93348db2862b6bad38091a9b0d3d1485479465802013`

The Docker registry TLS API returned index digest `sha256:05aa77262db9277fde6374bb2f901c9604b8a9373029e1a7993440c6aae48736`, which listed this linux/amd64 manifest. Fetching it **by digest** returned the same `Docker-Content-Digest` header and SHA-256 of its 2,867-byte response. Podman pulled only that immutable digest into its new private store and `image inspect` reported repo digest equal to the selection, local config ID `63fb01dbab2f21a30c1188f6b05319df39b786a5845a5541299ed0dc3ed5bc69`. This proves registry response integrity and correct image selection, **not** image signature, SBOM, reproducible build or broader supply-chain acceptance. The [Docker Official Image documentation](https://raw.githubusercontent.com/docker-library/docs/master/postgres/content.md) documents `POSTGRES_PASSWORD_FILE`, local Unix-socket trust, and PostgreSQL 17's persistent mount `/var/lib/postgresql/data`; [PostgreSQL's pg_dump documentation](https://www.postgresql.org/docs/17/app-pgdump.html) documents consistent exports.

`module postgres prepare|install|write|query|backup|restore|restored-write|restored-query|restore-remove|stop|remove [backup-id]` accepts **no arbitrary image, SQL, secret, host path or port**. New, owner-only `0700` directories: `/mnt/media/p0-v3/platform-lifecycle-sandbox/postgres-fixture` and `/mnt/media/p0-v3/backup/postgres-fixture`. A generated **fake** 64-character hex password is held only in the former's private `0700` `secrets/` directory in a `0600` file. Only `POSTGRES_PASSWORD_FILE=/run/secrets/p0v3-password` and the scoped read-only bind path enter Podman arguments; no password bytes enter CLI arguments, logs, source, test output or backup names. Data is a separate rootless-UID-mapped `data/` bind. Podman is rootless/local, `vfs` with private root/runroot, `--pull=never`, read-only container filesystem with scoped tmpfs, and memory/process limits. Only `127.0.0.1:15432:5432` is published for primary, `127.0.0.1:15433:5432` for isolated restore. No route, 443, systemd, account mutation, software_lab bind or ntfy store access.

## Actual result, 2026-10-30 UTC

1. `prepare` created exactly the new PostgreSQL directories and fake credential; `stat` confirmed `gerald:600` on the secret file and `gerald:700` on the backup namespace. The image initialized in the private Podman store. `ss` showed only **127.0.0.1:15432** listening. Fixed `psql` commands through the container's local Unix socket created `p0v3_sandbox_rows`, inserted `(1, 'first')` and queried `1:first`.
2. `backup first` executed `pg_dump -Fc` against the running test database (a consistent logical snapshot) and copied `backup.dump` to the dedicated backup namespace with SHA-256 manifest. The 1,941-byte file had SHA-256 `66191a8a8a156ba36478cbff7f501f22ae8b339763152fb1599c69cb94f7531d`. **First restore attempt failed**: `pg_isready` briefly passed for the official entrypoint's temporary server, then `pg_restore` hit `FATAL: the database system is starting up`. That failed isolated target was retained for diagnosis; its container was removed, and no successful restore was claimed for `first`.
3. Readiness was corrected to require two successful `SELECT 1` checks separated by stabilization. A new `backup second` from the unchanged primary yielded SHA-256 `1e0b06924572f984320fe328a947f8ecbb1518c2e3d8cfe489cbff98b8bf0309` (1,941 bytes). `restore second` verified the manifest, initialized a **different** empty data directory and PostgreSQL container on **127.0.0.1:15433**, then ran `pg_restore --exit-on-error`. Its query returned `1:first`; inserting `(2, 'restored')` in the restored target yielded `1:first` and `2:restored`. The primary still returned **only `1:first`**, demonstrating isolation. Both containers were stopped and removed.
4. Two additional main-container teardown/reinstall cycles against its retained `data/` succeeded; each queried `1:first`, repeated the idempotent fake write, then stopped and removed the container. The private `podman ps -a` was empty and `ss` showed **no** listeners at either test port afterward.
5. The independently opt-in **real** `PostgresRealIntegrationTest` completed successfully: fixed SQL write/query, consistent dump, hash verification, separate restore with the original row plus a new row isolated from the primary, and two teardown/reinstall cycles. Its retained 1,941-byte backup at `backup/postgres-fixture/it84k95pnrtx/backup.dump` has SHA-256 `9c9a586059a242edf96237467aeb39eb4875bafc4069560e426dcbcf12dfff98`. It left no active sandbox container or listener. Neither the fake secret nor any mapped PostgreSQL data directory was automatically deleted.

Ordinary `clean check` uses fake Podman commands and deliberately skips this real test. The database operations use the official image's container-local Unix socket; `ss` verifies **loopback binding**, but no separate host TCP/password client was accepted. Backup covers **one test database only**, not global roles, other databases, replication slots, WAL archiving or a production retention policy. Restored data is retained in an isolated target; no in-place production restore was attempted. This does **not** imply installed/accepted `postgres-ssd`, any other inventory component, or either required full-stack clean install/restore: **0/2**.
