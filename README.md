## Explicit host-local site plans (offline only)

`sites.json` is a **separate operator-supplied** schema, not the inventory. For example (the digest below is only a syntax example, **not** a verified/pullable image):

```json
{"schemaVersion":1,"sites":[{"id":"scratch","workloads":[{"id":"probe","image":"docker.io/library/busybox@sha256:aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"}]}]}
```

Commands: `site validate <sites.json> <site-id>`, `plan render <sites.json> <site-id>`, `stage offline <sites.json> <site-id> <temp-workspace>`, `stage restore <temp-workspace> <site-id>` (use `./gradlew run --args='…'`). The workspace must be an existing directory **beneath the system temp directory**, initially empty; subsequent operations require its site marker. Staging writes `current/` Quadlet files and a checksum manifest, saves one previous version, and restore rolls back one version (or removes the first stage). It rejects unexpected files and modified stages. It never starts containers, installs units, pulls images, publishes ports, mounts volumes, edits production directories, or manages live services. No active deploy or functional restoration is claimed.

Site/workload IDs are bounded slugs; workloads must be explicitly named, cannot reuse any inventory service ID, and require a SHA-256-pinned image reference. Unknown config fields (including secrets, environment, routes and mounts) are rejected. Render order is stable; each file uses `Network=none` and `ReadOnly=true`. The JSON render plan includes the Quadlet text and is safe to compare in tests, but should **not** be interpreted as acceptance of that image or application. The isolated staging and rollback tests check filesystem behavior only. Do not copy these files to a live Quadlet search path until an independently reviewed deployment, backup, functional restore and acceptance process exists.

## Restricted real rootless Podman probe (NOT the catalog)

A separate, opt-in `probe prepare|install|stop|remove <site> <sha256:image-id>` and `probe snapshot|restore <site> <sha256:image-id> <snapshot-id>` executor operates **only** inside an existing, owner-owned `0700` `/mnt/media/p0-v3/platform-lifecycle-sandbox` (or an injected temp-directory fake backend in unit tests). Its site is `probe-<site>` with a binding owner/image marker; a different image, linked directory, unexpected entry, broad sandbox permissions, existing container or unsupported site name fails closed. The pinned image **must already be in that site's isolated Podman store**: no image pull, mutable tag, host account change, or use of the normal Podman store. Podman is forced rootless, local, `vfs`, with site-private `--root`/`--runroot`, `--network=none`, no published ports, read-only root filesystem, dropped capabilities and a bind mount **only** to that site's `data/`. The command is fixed to `/bin/sleep 300`; arbitrary catalog units cannot be executed. `remove` stops and deletes only the named probe container, preserving data, snapshots and image store; it is **not a full teardown**.

`probe snapshot` requires the probe stopped and copies at most 32 flat regular data files of at most 1 MiB each into a new site-private snapshot with SHA-256 manifest. `probe restore` verifies the manifest and copies to a **new** `restores/<id>/`, never over `data/` or any production directory. No claim is made about database consistency, real application data, automatic backup scheduling, restart, or functional application recovery.

## Owner-only site contracts and non-executable workflow

`contract plan <site.json> <approved-hosts.json> <data-root> <backup-root>` reads two **owner-only, nonsymlink POSIX files** (no group/other access), without reading or writing any live service, secret, or host account. The approval file is a JSON array of DNS hosts reviewed **separately** from the site document. Both roots are absolute, normalized, nonoverlapping caller-supplied v3-only boundaries; the planner derives `<root>/<site-id>` but **does not attest that the roots are dedicated, safe, unmounted, or even present**. Do not pass production paths until a separate boundary review.

The strict site schema has `schemaVersion:1`, a bounded `siteId`, `modules` and `routes`. Every selected module must be one of the 46 named inventory modules, with **every** named component explicitly specified (no automatic inventory-to-container conversion). Each component requires an operator-chosen `DAEMON`, `ONE_SHOT` or `BUILD_ONLY` mode, a digest-pinned image, and a list of logical `secretKeys` (never secret values). Every module explicitly declares `dependsOn` and `persistence` (possibly empty); persistence identifies a component, a unique logical volume and an absolute container mount path. Missing dependencies, cycles, extra or partial components, duplicate mounts/volumes, unsafe images and plaintext secret fields fail closed. Routes are optional, target only declared daemon components/ports, and require exact approval by the separate host list; **approval here is not proof of DNS, Cloudflare, TLS or application readiness**.

The sorted JSON workflow includes explicit contracts, approved routes, dependency-ordered module install and reverse teardown *intents*. Teardown starts with required verified-backup and functional-test gates; backup intends stop/restart only explicitly declared daemon components and snapshot each declared persistent volume, then verify; restore intends an **isolated** restore and required functional test. None of these **contract-workflow** intents is executable: the separate restricted probe above is not a general module/route executor. No image pulls, Quadlet install, stack container/network setup, secret retrieval, account creation, application volume creation, stack backup data capture, teardown or restore is implemented here. The tests exercise selection, validation, CLI and ordering with temporary owner-only files, **not** a running stack or functional restoration. EULA acceptance and authoritative catalog names do not supply images, config, credentials, routes, dependencies or acceptance evidence.

## Offline SSO-to-Linux lane-account intents

The separate `lane plan <request.json> <trusted-issuer> <occupied-usernames.json>` command emits **JSON data only**. No useradd, account database reads, PAM changes, directory creation, SSO changes, or live service operations occur. Example request (identifiers are illustrative, not a verified SSO deployment):

```json
{"schemaVersion":1,"siteId":"scratch","issuer":"https://sso.example.test/realms/v3","humans":[{"subject":"opaque-human-a","username":"p0v3_alice"}],"agentSubjects":["opaque-agent-a"]}
```

The independently supplied trusted HTTPS issuer must **exactly** match the request. Subjects are bounded, case-sensitive opaque IDs; duplicates among humans or across human/agent identities are rejected. Each human has exactly one explicit bounded `p0v3_` username; duplicate names, reserved suffixes (including `gerald`, `software_lab`, `root`, `agent`), unsafe names, and names in the supplied occupied-username snapshot are rejected. The snapshot is a nonempty JSON string array of Linux usernames, e.g. `["root","gerald","software_lab"]`; the planner does **not** collect it from the host or assert it is fresh/complete.
